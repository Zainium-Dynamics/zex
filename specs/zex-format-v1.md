# Zainium `.zex` Package Format — Specification v1

> **DEPRECATED — July 2026**
>
> This document describes an experimental binary `ZEX1` container format that
> was never shipped in production. The **canonical runtime format** is the
> `tar.zst` layout documented in [`ZEX-FORMAT.md`](../ZEX-FORMAT.md):
> `manifest.toml` + `signature.b3` + `payload/` inside a zstd-compressed tar
> archive. All `zex install`, `zex fmt`, and upgrade paths use that layout.
> This spec is retained for historical reference only — do not implement new
> tooling against the `ZEX1` binary header described below.

Status: **Deprecated** (superseded by `ZEX-FORMAT.md`)
Applies to: Zainium OS package & rootfs distribution (historical)

## 1. Goals

- Single-file, signed, integrity-checked package format for Zainium OS.
- Built on top of `zstd` for payload compression (no custom compression
  algorithm — we deliberately reuse a battle-tested codec and focus our
  engineering effort on the container, policy, and signing layers).
- Enforce Zainium OS's filesystem layout convention: **no `/usr` merge**.
  Packages must lay files out under traditional root-level directories
  (`bin/`, `sbin/`, `lib/`, `etc/`, `share/`, ...), matching how the
  package will be placed on a Zainium root.
- Detect, at pack time, any reference (path entry OR text content) to
  `usr/` that would indicate the package was built for a `/usr`-merged
  distro and is incompatible with Zainium's root layout.

## 2. Non-goals

- This format does not implement a general-purpose malware/virus
  signature database. The `integrity scan` step described below is a
  **structural and policy check** (does the archive match its manifest,
  does it violate path policy, does it contain unexpected setuid bits,
  etc.) — not antivirus heuristics. Reports describe exactly what was
  checked; they do not claim broader malware-detection coverage than
  what is implemented.

## 3. File Layout

A `.zex` file is a flat binary container with four sequential sections:

```
┌──────────────────────────────────────────┐
│ [0] MAGIC + VERSION        (8 bytes)      │  "ZEX1\0\0\0\x01"
├──────────────────────────────────────────┤
│ [1] HEADER (fixed size)                   │  offsets/lengths of below
├──────────────────────────────────────────┤
│ [2] MANIFEST (JSON, UTF-8)                 │  package metadata
├──────────────────────────────────────────┤
│ [3] SECURITY REPORT (JSON, UTF-8)          │  structural scan results
├──────────────────────────────────────────┤
│ [4] SIGNATURE BLOCK                        │  ed25519 + blake3 + sha512
├──────────────────────────────────────────┤
│ [5] PAYLOAD (zstd-compressed tar stream)   │  actual file tree
└──────────────────────────────────────────┘
```

### 3.1 Header

Fixed 64-byte binary header (little-endian):

| Field              | Type   | Size | Description                          |
|---------------------|--------|------|---------------------------------------|
| magic               | bytes  | 4    | `"ZEX1"`                              |
| format_version      | u16    | 2    | Currently `1`                         |
| manifest_offset     | u64    | 8    | Byte offset of manifest section       |
| manifest_len        | u64    | 8    | Length in bytes                       |
| report_offset       | u64    | 8    | Byte offset of security report        |
| report_len          | u64    | 8    | Length in bytes                       |
| signature_offset    | u64    | 8    | Byte offset of signature block        |
| signature_len       | u64    | 8    | Length in bytes                       |
| payload_offset      | u64    | 8    | Byte offset of zstd payload           |
| reserved            | bytes  | 2    | Reserved, must be zero                |

### 3.2 Manifest (JSON)

```json
{
  "name": "nano",
  "version": "1.3.7",
  "description": "Small terminal text editor",
  "features": ["cli"],
  "built_at": "2026-06-20T10:00:00Z",
  "builder": "Zainium Official Builder",
  "file_count": 42,
  "uncompressed_size": 184320,
  "layout_policy": "zainium-no-usr-merge-v1",
  "files": [
    { "path": "bin/nano", "size": 184000, "mode": 755, "sha256": "..." },
    { "path": "etc/nanorc", "size": 320, "mode": 644, "sha256": "..." }
  ]
}
```

### 3.3 Security Report (JSON)

Generated by `scanner.rs` / `root_guard.rs`. Describes **only** what was
actually checked — no unverified claims.

```json
{
  "schema": "zainium-security-report-v1",
  "layout_check": {
    "policy": "zainium-no-usr-merge-v1",
    "result": "passed",
    "rejected_paths": []
  },
  "content_scan": {
    "description": "Text files scanned for literal '/usr' path references",
    "files_scanned": 12,
    "matches": []
  },
  "manifest_integrity": {
    "result": "passed",
    "description": "Every file in archive matches a manifest entry and hash"
  },
  "permission_audit": {
    "result": "passed",
    "setuid_files": [],
    "description": "No unexpected setuid/setgid bits found"
  }
}
```

### 3.4 Signature Block

Contains, for each enabled scheme, a signature over the **blake3 hash of
the concatenation of (header || manifest || report || payload)**:

```json
{
  "signed_by": "Zainium Official Builder",
  "blake3_digest": "<hex>",
  "signatures": {
    "ed25519": "<hex signature>",
    "sha512": "<hex digest, for redundancy>"
  }
}
```

Only the Zainium official signing key is supported in v1 (no maintainer
key chaining yet — single trusted key model).

### 3.5 Payload

A zstd-compressed tar stream of the package's file tree, rooted exactly
as it will be placed on a Zainium root (e.g. `bin/`, `sbin/`, `lib/`).

## 4. Layout Policy — `zainium-no-usr-merge-v1`

Enforced at **pack time**, before any compression or signing happens.

### 4.1 Path structure check

Any archive entry whose path starts with `usr/` (in any form: `usr/`,
`./usr/`, `/usr/`) causes immediate rejection:

```
✖ Rejected: path 'usr/bin/foo' found.
  Zainium OS does not use the /usr merge — this package does not
  represent a valid Zainium root layout.
```

Allowed top-level directories (configurable allow-list):
`bin`, `sbin`, `lib`, `etc`, `share`, `var`, `opt`, `boot`, `root`, `home`.

### 4.2 Content scan

Text-like files (scripts, configs — determined by extension and a
binary/text heuristic on content) are scanned for literal substrings
`/usr/` or `usr/` that look like filesystem path references. Any match
causes rejection with the file path and line number reported, so the
maintainer can fix the source.

Binary files are **not** content-scanned for this check (string matches
inside compiled binaries are not reliable signal and produce false
positives); they are still covered by the path-structure check above.

### 4.3 Override

There is no `--force` override for the layout policy in v1. A package
that references `/usr` is not a valid Zainium package, full stop. If a
legitimate exception is ever needed, it must be a deliberate policy
version bump (`zainium-no-usr-merge-v2`), not a per-package flag.

## 5. CLI Surface

```
zex fmt pack <directory> --version <ver> [--sign ed25519,blake3,sha512] [--report]
zex fmt unpack <file.zex> [-o <dir>] [--verify-only]
zex fmt verify <file.zex>
zex fmt inspect <file.zex>
```
